# The web UI is server-rendered with axum and Datastar

`scree web` serves the web UI from the same binary. Pages are rendered on the server (maud templates) and patched into the browser by Datastar over server-sent events. There is no JavaScript build step and no client framework. The server is axum 0.8 with the `datastar` crate's `axum` feature. The Datastar 1.0.x script, `tokens.css` and the app stylesheet are embedded in the binary (`include_str!`) and served with ETags. Commands stay plain functions over a `rusqlite::Connection`: each request opens its own connection and runs the command in `spawn_blocking`, so a write from the web is the same `BEGIN IMMEDIATE` transaction as one from the CLI. The `PRAGMA data_version` poller in `tui/watch.rs` moves to the library and runs once per process, feeding a `tokio::sync::watch` channel that every open SSE stream listens to, so a CLI write reaches an open page within about a second. Styling follows `docs/design-system.md`.

A server-rendered page gives one code path for the first load, the response to a mutation and a live push: render a fragment, patch it by id. The library already produces the typed values the templates need (`ticket::build`), so no JSON API layer duplicates the contract, and the nix build needs no node toolchain. axum is the Datastar SDK's primary target and is actively maintained.

Rejected:

- Rocket with the `datastar` crate's `rocket` feature. It works, but on toy servers it added about 71 crates, +4.2 MB and 2.7 times the cold build CPU of axum's about 35 crates and +1.2 MB (single runs, not stripped). The SDK feature is pinned to `rocket ^0.5`, while Rocket 0.6 is at a release candidate with breaking changes, after a gap of about 29 months between 0.5.1 and 0.5.2.
- A synchronous server (`tiny_http`, `rouille`). Lighter, but last released in 2022 and 2023, with no Datastar integration, so SSE would be hand-framed, one thread per stream. `tiny_http` is the pick only if avoiding an async runtime ever outranks maintenance.
- HTMX. Client-only state (selection, keyboard, optimistic updates) would need a hand-written layer that Datastar's signals provide.
- A single-page app. It needs a JSON API that duplicates the library's output contract, and a node toolchain.

Datastar's own Rocket (its web-component API, currently beta) is not used for pages. It may be used for client-only widgets such as the graph viewport, only after the spike shows it works with SSE morphing. Use light mode so `tokens.css` applies, and pin the bundle. The licence was read (v1.0.5, MIT, copyright Star Federation): embedding the bundle in the binary is allowed provided the copyright and permission notice ship with it. The terms and the bundle sha256 are recorded in `src/web/assets/DATASTAR-LICENSE.md`.

Consequences: Scree gains an async runtime (tokio) and about 35 crates. The reason is that live push and many long-lived connections need an async HTTP server, and hyper handles the HTTP edge cases. `scree web` is a process the user starts, not a daemon, and the database stays the only shared state, so "no server" in `AGENTS.md` now means no always-on service. It binds `127.0.0.1` by default and runs as Role human, like the TUI. Every POST and SSE request checks `Host`, `Origin` and `Sec-Fetch-Site`, which blocks DNS rebinding and cross-site writes to a database the page can modify. A non-loopback bind is refused unless a per-process token is configured; that rule was not set here. [ADR 0004](0004-web-server-contract.md) sets it: a non-loopback bind needs `--i-know-this-is-open` and has no token. Datastar's default build evaluates expressions with `eval`, so the Content-Security-Policy must allow `'unsafe-eval'`; a nonce or hash does not help, and under a policy without it the page does not run. The policy the server sends is `default-src 'none'; script-src 'self' 'unsafe-eval'; style-src 'self'; connect-src 'self'; img-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`. That is acceptable here because the server serves only its own scripts and escapes all content, but it rules out a stricter policy. Without JavaScript the page shows no Decision detail. `cargo audit` and `nix flake check` must pass with the new dependencies.

A tracer-bullet spike (the Decisions queue as one screen, behind a hidden `scree web` command, on the branch `spike/web-ui`) tested the design. Results, measured on macOS against a temporary database:

1. A CLI write reached the open page in about 0.5 seconds, and focus, typed text, scroll position and the input node survived Datastar's morph with no special patch mode.
2. With four SSE streams open, SIGINT exited in 0.06 seconds and every handler logged its close. Closing a tab ended its handler. A 2 second cap on shutdown is in the code.
3. 264 concurrent POSTs ran beside 282 CLI writes with no `SQLITE_BUSY` and no database errors. Refusals (agent role, already decided) render inline.
4. j/k/Enter/Esc/? work and are suppressed while typing. An optimistic update rolled back with its inline error in about 150 ms. The CSP above is required.
5. A foreign `Host`, a foreign or `null` `Origin`, and `Sec-Fetch-Site` of `cross-site` or `same-site` are rejected on POST and SSE GET, covered by tests. Loopback is the only bind. Assets answer 304 on a matching ETag.
6. `nix build`, `cargo nextest run`, clippy, fmt and `cargo audit` pass. The stripped release binary grew from 4,490,880 to 5,666,448 bytes (+1.18 MB). `Cargo.lock` grew by 28 packages (tokio, axum, datastar, maud, futures-util and their dependencies).

Not tested: Linux builds, phone width and accessibility checks of the page, and a real in-page write conflict in a browser. The spike moved the `data_version` poller into the library as a callback variant (`watch::spawn_with`) and left the TUI's entry point as it was, so the poller is not yet a tokio task. The spike returns refusals as HTTP 200 with an `X-Scree-Error` header, which the full build may change. Datastar's Rocket web-component API was not tried.
